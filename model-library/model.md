# Domain model rules

Conventions for the classes of a model library: the entities of the domain, which travel as JSON between front,
back and storage.

## Rules

- **A `*.model.ts` file holds contracts and definitions, never logic**: classes with the defaults their
  constructors apply, interfaces, types, enums and constant definitions (tables, catalogues). No function is
  declared in it; a constructor that needs to convert its input calls a function from a function module. An ESLint
  `no-restricted-syntax` rule fails on a function declared in a model file.
- **The shape of a class follows [angular/class-model.md](../angular/class-model.md)**: one class per entity with
  its `<Name>Parameters` interface, a single destructured constructor argument, defaults in the destructuring,
  required fields before optional ones, alphabetical order everywhere, `is*` booleans.
- **A model holds data and nothing else**: fields and a constructor that applies the defaults. No methods, no
  getters, no callbacks. A model reaches every consumer as JSON sooner or later, and JSON has no prototype.
- **Whatever works on a model is a function**, in a function module next to it: copying, validating, deriving a
  state (`cloneDocumentItem(item)`, `isResolvedReference(reference)`). It reads plain fields, so it gives the
  same answer on an instance and on the JSON of one.
- **A function that behaves per type dispatches through a table**, `Record<ItemType, (item) => Result>`, never a
  `switch` nor `instanceof`: the compiler then demands an entry for every type, so a new type cannot be forgotten
  in one of them.
- **A type is told apart by a field, never by its class.** Every family has a discriminant (`type`,
  `expectedType`) that survives serialisation.
- **JSON is turned back into instances by hydration functions**, which apply the defaults a field added later
  needs. Code that receives a document hydrates it before using anything the classes provide.
- **An enum has string values**, the same ones that are stored, so a stored document stays readable, and its
  members go in alphabetical order (`perfectionist/sort-enums`): with explicit values the order changes nothing.
- **An id is generated by the constructor default**; a copy of an entity gets a new one.
- **A model file declares, in this order**: enums, types, other interfaces, classes and their `Parameters`
  interfaces, each group alphabetical. Inside a class: required fields,
  optional fields, constructor. Inside an interface: required members, a blank line, optional members.
  `perfectionist/sort-modules`, `sort-classes` and `sort-interfaces` enforce all three and fix them on save.

## Example

```ts
export class TextItem extends DocumentItem {
    link: string;
    styles: TextStyles;
    text: string;

    hasSpaceBefore?: boolean;

    constructor({ customName, hasSpaceBefore, id, link = '', styles = new TextStyles({}), text = '' }: TextItemParameters) {
        super({ customName, id, type: DocumentItemType.Text });
        this.hasSpaceBefore = hasSpaceBefore;
        this.link = link;
        this.styles = styles;
        this.text = text;
    }
}

const ITEM_CLONERS: Record<DocumentItemType, (item: DocumentItem) => DocumentItem> = {
    [DocumentItemType.Text]: item => {
        const text = item as TextItem;

        return new TextItem({
            customName: text.customName,
            hasSpaceBefore: text.hasSpaceBefore,
            link: text.link,
            styles: new TextStyles({ ...text.styles }),
            text: text.text
        });
    }
    // one entry per DocumentItemType, or the file does not compile
};

export function cloneDocumentItem<T extends DocumentItem>(item: T): T {
    return ITEM_CLONERS[item.type](item) as T;
}
```
