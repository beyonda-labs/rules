# Translation rules

Conventions to follow when adding or changing translations.

## Rules

- **Keys live next to the code that uses them**, never in the merged bundle: `<module>/assets/<module>.<lang>.json`
  for a component, `<page>/assets/<page>.<lang>.json` for a page, and `shared/assets/<topic>.<lang>.json` for what
  several pages of an app render, one file per topic (`shell`, `roles`, `permissions`). A module without an
  `assets/` folder gets one.
- **The merged `en.json` / `es.json` are generated artefacts and are never edited by hand.** Anything written there is lost on the next merge, silently.
- **After touching any translation, the bundle is regenerated** with `pnpm run merge-translations`, and the result is committed with the change.
- **The first node is the namespace of the repo, the second is the module or the topic of a shared file**:
  `angular-components.tabs.*`, `document-builder.editor.*`. A module owns that node and is the only one that writes
  in it, so a vocabulary several pages render, such as the names of the roles, is a topic of `shared/assets/` and
  never the node of one of those pages.
- **A shared node is contributed to, never taken over**: where a service renders text on behalf of others, each
  contributor writes only its own part of it. Two files never define the same key, because the merge would silently
  keep one of them; `bey-check-translations` refuses it inside a repo.
- **The errors of the backend live under `angular-components.http.error.<domain>`**, and their titles under
  `.http.title.<domain>`, the domain being the first part of the `messageKey` (`edit-locks`, `sharing`, `entities`;
  see [error.md](../express/error.md)), since the library's HTTP service builds the key from it. The module that
  sends those requests writes them, in the library's namespace even from an app, and two modules that send
  requests of one domain share its node key by key.
- **Every `.en.json` has its `.es.json` with exactly the same keys.** A key added in one language and not the other is a broken build, not a pending task.
- **Key names are kebab-case**: `select-all`, `close-confirmation`. Never camelCase, never snake_case.
- **The shape of a key is `<namespace>.<module>[.<submodule>][.<group>][.<subgroup>].<key>`**, six levels at
  most. Namespace and module are fixed; the three in between are optional and each appears at most once.
- **Below the module, two levels are the norm and more is a smell**: it usually means the module needs
  splitting rather than another node.
- **A key is named after what it says, not where it sits**: `empty`, `max-size`, `unsupported-type`. Not `label-1`, not `text`.
- **No key without a user-visible string behind it**: a node exists because something renders it.

## Example

```
src/lib/components/tabs/assets/tabs.en.json
src/lib/components/tabs/assets/tabs.es.json
src/lib/services/edit-lock/assets/edit-lock.en.json
src/lib/services/edit-lock/assets/edit-lock.es.json
```

```json
{
    "angular-components": {
        "tabs": {
            "label": "Navigation tabs",
            "more": "More tabs",
            "overflow": {
                "empty": "No more tabs"
            }
        }
    }
}
```

```json
{
    "angular-components": {
        "http": {
            "error": {
                "edit-locks": {
                    "held": "{{holderName}} is editing it: your changes were not saved."
                }
            }
        }
    }
}
```

```html
<span>{{ 'angular-components.tabs.more' | translate }}</span>
```
